# Shared Tasks 0.4: compatibility, upgrade and downgrade

What happens to a vault's notes and its sync data when Shared Tasks moves
between 0.3.x and 0.4 (LFCP-02-055, MVP-0.2-COMPATIBILITY-AND-MIGRATION
§11–§12). Text for the release notes is at the end.

## Two kinds of shared content, side by side

- Shared tasks from 0.3.x (Shared Objects collaborations) keep working as they
  are: same collaborations, same identity, same queued changes. Nothing is
  converted.
- Shared sections (0.4) are new collaborations of their own. Each stored
  collaboration is opened by its own data profile; neither path ever writes
  to the other's.
- Moving 0.3.x shared tasks into a section is an explicit copy ("Share
  section…" offers it): the copy gets new identities, and the old
  collaboration continues separately.

## Sync data on this device

The sync data (IndexedDB, in Obsidian's profile directory, outside the vault)
is upgraded the first time 0.4 opens it:

- its local state is encrypted at rest (LFCP-02-098);
- the database moves to version 2, so an older plugin cannot open it and read
  encrypted rows as if they were plain.

Queued changes, the identity, keys and projection bindings are kept exactly.
The notes themselves (Markdown) are never changed by the upgrade. The first
start that upgrades says so once: "Shared Tasks upgraded its local data.
Going back to a version before 0.4 will not open it; your notes are
unchanged."

## Matrix

| Plugin on this device | Sync data written by | Result |
| --- | --- | --- |
| 0.4.x | 0.3.x (or none) | Upgraded once; everything keeps syncing |
| 0.4.x | 0.4.x | Normal |
| 0.4.x | a newer plugin (database version above 2) | Sync stops with "This vault's sync data on this device was written by a newer version of Shared Tasks. Update the plugin to sync again. Your notes are not changed, and the sync data is left as it is." Nothing is written or deleted |
| 0.3.x | 0.4.x (upgraded) | 0.3.x cannot open the sync data and does not sync; its settings show "Shared Tasks could not start: VersionError …". Nothing is written or deleted; notes stay readable and editable. Installing 0.4.x again picks up where it left off |
| 0.3.x | — joining a shared section | Refused before the invitation is used: "needs a newer version"; the link still works after updating |

## While the plugin is off or too old

Notes stay readable and editable. Edits made then are local changes of the
note. When 0.4 runs again, they are compared with the shared state through the
projection's stored base: changes on both sides merge, as for any edit. A note
with no stored base is compared before anything is sent (the section shows as
needing review); nothing is overwritten or published blindly.

## Evidence

- `test/core/lfcp/compatibility.test.ts`: upgrade from storage opened as 0.3.x
  opens it, with a pending legacy edit (CM01); a section beside legacy Tasks
  with profile dispatch (CM02); a newer storage refused without writes; edits
  made while the plugin was off merging with a collaborator's change (CM10).
- `test/core/collab/live-sections.test.ts`: a client without the sections
  profile refuses a section invitation without using it (CM03).
- Section fixtures MS11 and `test/core/sections`: a lost base is not guessed
  (CM11).
- sdk-ts (LFCP-02-029): the version 2 database and the refusal by a released
  0.3.x build.

## For the release notes

> **Updating to 0.4.** Your shared tasks keep working as before. Shared
> Tasks upgrades its sync data on this device the first time 0.4 starts: it
> is encrypted at rest, and earlier versions can no longer open it.
>
> **Going back.** After updating to 0.4, Shared Tasks cannot go back to
> 0.3.x on this device: its local sync data is upgraded and encrypted.
> Downgrade only to 0.4.x or later. Your notes are not affected. If a 0.3.x
> plugin shows "Shared Tasks could not start: VersionError", that is why:
> install 0.4.x again, and its data is intact.
