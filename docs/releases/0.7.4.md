# Shared Tasks 0.7.4 (draft)

> Draft, written with the change. It becomes final in the release commit,
> which adds the version, the date and the checksums.

Shared Tasks 0.7.4 helps a device get back a section key it lost, gives up
on a key the server keeps refusing only when you say so, and lets you
remove what an earlier identity left on this device. For catalog users
updating from 0.7.3.

**Requires Obsidian 1.13.4 or later**, as 0.7.3.

The Markdown format of your notes and the sync protocol are unchanged. It
uses the OpenLFCP SDK 0.5.2.

## What changed since 0.7.3

- **A lost key comes back.** A device that should read a section but lacks
  its key (its package was lost, or its key store was reset) asks your
  other devices for it. Your first device, or another with Full access,
  sends it again the next time it is open. "Your devices…" shows "Phone
  asks for the key of "Plans"" there, and the waiting state on the device
  itself.
- **Send keys again.** In "Your devices…" on your first device, each of
  your other devices has **Send keys again**: every section key, sent to
  that device again. Use it for a device with Read access, which cannot ask
  by itself.
- **Stop trying, Try again.** When a section's key changes and its server
  refuses the new key to some readers every time, "Your devices…" lists it
  with the server's answer and **Stop trying**. Those readers can't read
  changes made after the key change until it is sent. The item then waits
  under **Given up**, where **Try again** sends it once more. A key change
  that may still be in place is never offered.
- **Delete earlier identity data.** "Create a new identity" leaves the
  previous identity's keys and local data on this device. Settings →
  Shared Tasks now shows them, with **Delete earlier identity data…**. Only
  on confirmation; changes it had not sent are lost, and your notes are
  not affected.
- **Fewer failed approvals.** Approving, adding or removing a device and
  changing a section's key no longer fail when this device's open section
  stored the same record first.
- **The headless bridge on Windows.** `lfcp-node pair` now starts on Windows.

## Install and upgrade

From Settings → Community plugins → Updates. Nothing to migrate.

By hand: put `main.js`, `manifest.json` and `styles.css` from the release
page into `<vault>/.obsidian/plugins/shared-tasks/` and compare them with
the checksums (added in the release commit).

## Rolling back to 0.7.3

Before you downgrade:

1. In "Your devices…", choose **Try again** on everything under **Given
   up**, and let it finish.
2. On your first device, choose **Send keys again** for each device you
   are about to roll back.

Then install 0.7.3 over 0.7.4. The data format is the same, but:

- **A key change you stopped trying stays stopped.** 0.7.3 neither retries
  it nor lists it, so other people's devices keep waiting for that key
  until 0.7.4 is installed again and **Try again** is used. Your own devices
  still get it the next time your first device brings your devices up to
  date.
- **A request for a key stays in your device list.** A device that asked
  for a key before the rollback keeps asking: 0.7.3 does not clear its
  request. Your first device, on 0.7.4, answers it once a day.
- A 0.7.3 device does not ask for a key it lacks.

## Known limits

The limits in [0.7.3](0.7.3.md#known-limits) still apply, except that a
refused key can now be given up.

- **Earlier identities from 0.7.2 and 0.7.3 are not listed.** Only a new
  identity created with 0.7.4 or later is recorded, so data left by a new
  identity created in 0.7.2 or 0.7.3 stays and is not offered for deletion.
- **A device with Read access cannot ask for a key.** Use **Send keys
  again** on your first device. The same applies when the missing key is
  the device list's own current key.
- **Stop trying is per key change.** It covers every reader that key change
  still owes; it cannot give up one device and keep another.
- The new actions were tested with simulated devices and against the
  reference server, but not on a real iPhone or iPad with an iCloud-synced
  vault.
