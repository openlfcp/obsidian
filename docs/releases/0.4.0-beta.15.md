Shared Tasks 0.4.0-beta.15: the fifteenth beta with shared sections.

A pre-release for testers through BRAT: the community directory and
Obsidian's own updates keep offering 0.3.x.

## New since 0.4.0-beta.14

**Your offline edits are no longer undone when a collaborator is removed
meanwhile.** If you edited a shared section offline while its owner
removed someone else, your edits used to be undone silently when you came
back online. A changed title or a move went back to how it was. A new task
stayed in your note but never reached the others. Nothing said so. Now
Shared Tasks sends your edits again once you are back online, in the order
you made them, and the section card says "N offline edits from before an
access change are being sent again" until they are sent. If someone else changed the same task
meanwhile, or the server refuses an edit, the section needs your
attention. The card says that N offline edits could not be sent after an
access change. "Review conflicts…" lists each of them: **Keep** sends it
again, after the other change, and **Discard** drops it, so your note
shows the shared version. Until you choose, your note keeps your edits and
is never overwritten.

**A cut no longer comes back from another copy of the section, and Move
line moves the task you moved.** Shared Tasks remembered your last cut for
every later edit, in every note. That had two effects:
- With the same section open in two notes, a task you cut in one of them
  came back within a second, because the other note still showed it.
  Pasting the task then placed it twice.
- A Move line next to a task you had cut and pasted earlier sent that
  task as the one moved, not yours. A collaborator's move of your task
  then won without a conflict.

Now a cut only counts for a paste of it in the note it came from. It is
forgotten once it is pasted or once you cut something else. The other copy
removes the cut task too.

**A vault removed from a section is told so.** Opening a new invitation to
a section you were removed from used to say "this device is already in
that collaboration", as if nothing were wrong. Now it says "You were
removed from this section. Rejoining a section you were removed from isn't
supported yet; your local copy stays on this device." The invitation is
not used, and nothing changes. The section card of a vault whose changes
the server no longer accepts (removed, refused, or not a member) no longer
says "Current as last checked with the server" or "You can edit this
section". It says "Not synced: the server does not accept changes from
this vault for this section", and lists its waiting updates as "not sent:
the server does not accept them".

**Backspace and other edits can no longer glue a task to its hidden ref
line.** Live Preview hides the line that ties a shared task to its
section. A guard already stopped a Backspace at the start of the line
after it from joining the two. Some edits still got through: a join that
keeps the list marker, two joins at once, or text pasted onto the hidden
line. Any edit of yours that would put that line on one line with other
text is now refused. Backspace moves the caret to the end of the visible
line above, as before. Undo, redo and edits by other plugins are not
affected.

**Install with "Latest version" in BRAT.** BRAT never updates a beta added
with a specific version: it stays on that version. Earlier release notes
told you to pick one, and later betas then never reached you. See
"Stuck on an older beta?" under [Install with BRAT](#install-with-brat).

**A copy of a section that differs from the shared version says so.**
Two members' notes could show a section's tasks nested differently while
both badges said everything was up to date. After every sync a note is
now compared with the shared version: if a task sits somewhere else, the
badge no longer says it is current, and the section card says "One copy of
this section differs from the shared version". Shared Tasks tries once
more to put the task in place; usually that settles it.

**Two causes of such differences are fixed:**
- A task a collaborator added under a task indented with a tab, among
  subtasks indented with spaces, was shown one level too deep, under the
  subtask above it.
- When a collaborator moved the last task of a list away, the blank line
  before the paragraph after the list went with it, and Live Preview
  showed the paragraph's hidden marker line.

**A task you paste while a section waits for "Review conflicts…" stays
where you pasted it.** If you cut a task, a collaborator moved it at the
same time, and you pasted it elsewhere before choosing **Keep**, your note
kept it where you pasted it while everyone else saw it where the
collaborator had moved it. Now your paste is sent, and everyone sees the
task where you put it.

**Typing right after sharing a section rarely leaves it waiting any
more.** If you started typing in a section right after sharing it, before
Shared Tasks had finished setting it up, your first edits could stay in
your note without reaching anyone, and the section said it needed your
attention. In most cases they are now sent like any other edit; see Good
to know.

**A share you gave up before it reached the server leaves nothing behind.**
If sharing a section was interrupted before it reached the server and was
then given up, its local data stayed on your device for good. It is now
removed, and sharing that section again works as usual.

**Editing a shared section offline stays fast, even after many edits.**
Each change used to check every waiting update twice, so typing slowed
down the longer you worked offline.

**Quitting Obsidian in the middle of a sync no longer doubles an edit or
holds a section.** A restart at the wrong moment could apply an edit to a
task's title twice ("Draft v2 v2"), keep an update "waiting" on the
section card for good after offline edits were sent again, or take a task
you had just deleted for a damaged link and stop the section from syncing
until it was repaired. A restart now picks up each of these where it
stopped.

**Requires Obsidian 1.13.4 or later.**

## Good to know

**Rare: typing in the first moment after sharing can still leave the
section at "needs your attention".** Your first edits stay in your note
but are not sent until the note matches the shared version again. If it
happens, undo those edits, wait until the badge no longer shows attention,
then make them again. A fix is in progress.

## What it is

The features of 0.4.0, described in [0.4.0.md](0.4.0.md): share a whole
section of a note ("Share section…"), with its tasks, paragraphs and lists,
end-to-end encrypted, each section its own collaboration. Shared sections
are on in this beta: there is nothing to turn on.

## Before you install

> **No way back to 0.3.x on this device.** The first start of 0.4 upgrades
> Shared Tasks' sync data on the device and encrypts it at rest. A 0.3.x
> plugin can no longer open it ("Shared Tasks could not start:
> VersionError"); install 0.4.x again and the data is intact. Your notes are
> not affected.

- Try it in a test vault first, or keep a copy of your vault.
- A collaborator still on 0.3.x cannot join a shared section; their shared
  tasks keep working with yours.
- Collaborators on a shared section should all update to this beta. A
  member on a beta before 0.4.0-beta.14 can keep undoing the others' edits
  while their note is open, and a member on a beta before 0.4.0-beta.4
  keeps seeing "Needs your attention" after someone else chose **Keep it
  deleted**.

## Install with BRAT

1. Install BRAT from the community plugins.
2. Run "BRAT: Add a beta plugin for testing" with `openlfcp/obsidian`. In
   the version field choose **Latest version**: a specific version stays
   installed, and BRAT will not update it.
3. Enable Shared Tasks. Settings → Community plugins lists it as
   version 0.4.0-beta.15. If it lists an earlier version, see below.

If an earlier 0.4.0 beta is installed, BRAT updates it ("BRAT: Check for
updates to all beta plugins"); your identity, collaborations and settings
are kept.

**Stuck on an older beta?** In BRAT's settings, find `openlfcp/obsidian` in
the beta plugin list. If it shows a version, it is pinned there: edit it and
choose **Latest version** (or remove it and add it again with Latest
version), then run "BRAT: Check for updates to all beta plugins". BRAT's
setting "Select latest plugin version by default" saves choosing.

To turn shared sections off, quit Obsidian, add `"sectionsDisabled": true`
to `.obsidian/plugins/shared-tasks/data.json`, and start it again.

## What to report

"Export diagnostics…" prepares a report without note text, names, paths,
keys or links, and shows it to you first. Attach it to an issue at
https://github.com/openlfcp/obsidian/issues with what you did and what you
saw.

## Known limits

The limits of [0.4.0.md](0.4.0.md#limits) apply: about 200 tasks per
section is the qualified size, sections are read-only on mobile, and there
are no headings inside a section.

- **Rejoining a section you were removed from** isn't supported yet. Your
  local copy stays on your device.
- **Project server quotas.** The project server (sync.openlfcp.org)
  currently lets one identity host up to 200 collaborations (each shared
  section is one), up to 50 new ones a day from one network, 256 MiB of
  stored data in all and 128 MiB per collaboration. Past a limit, the
  action is refused with "quota exceeded"; nothing already shared is lost.
  These values may change, and the server's operator can set other limits
  for an identity. A server you run yourself sets its own.

## Under the hood

- Own offline work a Key Epoch cut off (§19.1) is re-applied
  (`src/core/sections/stale-work.ts`). Every commit is recorded as an own
  operation, with its units, intents and the fingerprints of the nodes it
  touched. When a Key Epoch cuts own units off, the section's passes are
  guarded (engine skip "stale-work") until each operation is re-committed
  under the fixed ID `<id>:reapply`, causally after every remote change. A
  restart in the middle finds the receipt and writes nothing twice. A node
  changed meanwhile, or a refused commit, goes to Review conflicts.
  Diagnostics: `sections.staleDiagnostics`. New live tests and the native
  spec section-stale-epoch, on 1.13.4 and 1.14.4.
- The session's last cut (`src/core/sections/session-cut.ts`) is a paste
  only where a user's paste re-inserts its bindings, in the note it came
  from, and never a move hint on its own. The three two-pane cases skipped
  with TODO(stale-cut) now run: 11/11 on 1.13.4 and 1.14.4.
- Join answers "removed" (access revoked or refused, or the server
  refusing the Resource with AUTHORIZATION_FAILED) before any claim. See
  the design note `rejoin-after-removal` in openlfcp/.github.
- The binding-line guard checks the result of a user's change, whatever
  its shape. New native spec: Backspace at the start of a Task line.
- New: the coordinator idle property test (a collaborator's edits in a row
  while the note is idle, through the section editor), and happy-dom
  20.14.5 (dev) for editor tests with a DOM.
- After a pass, the note as written is compared with the model it was
  projected from (`remote.ts` `misplaced`): a node under another parent, or
  out of the model's order among siblings both show, makes the projection
  "diverged", never CURRENT, unless its placement waits for the user's edit
  or a frozen section. The editor passes such a note once more.
- The structural writer gives a placed node the indentation of its parent's
  first list child, and moves a subtree's trailing blank line with it only
  when a blank line or the section's start comes before it.
- A bound node the note shows and the projection's base does not know,
  active in the model, is taken into the base as the note shows it; a
  placement elsewhere than the model's is sent.
- A restart in the middle of a pass or a re-apply: the base records the
  operations it includes (`StoredBase.applied`), the units of settled
  re-applied work wait in local state ("stale-to-discard") until discarded,
  and a new operation is first stored with its batch (at ids-allocated).
- A pass that changed and committed nothing (a section's first base,
  seeded while the note equals the model) keeps its bases when the user's
  edit lands during it (a keystroke, an IME composition opening, a closed
  note's file rewritten); nothing is written into the note. It used to be
  abandoned whole, and the section stayed at base-unknown.
- The stale-work guard asks storage once a pass (an indexed query of the
  quarantined units), not twice per outbound unit. See the performance
  re-check in `docs/devel/reports/section-performance-headless.md`.
- A section Resource discarded before hosting is deleted when it was never
  sent (`deleteUnsentResource`, SDK 0.2.0-beta.7); a stop in between leaves
  it marked, and the next start deletes it.
- The peer-structure property test and the native checks compare each
  note's nesting with the model's, not only the order; it found the
  indentation fix above. New native specs: section-nest-move, a restart of
  the plugin in the middle of a pass, and other plugins changing a shared
  section; Review conflicts beyond placement, resolved by either member in
  each order.
- `@openlfcp/*` 0.2.0-beta.8 (exact versions, from npm with provenance,
  dist-tag `beta`): after a member's first unit in a Resource went stale,
  the next unit names no previous unit (LFCP-WIRE-01 §26.2), so offline
  edits that were your first in a section are sent again too. Spec
  `mvp-0.2-baseline.12`, the reference server at `138030a`, 49 fixtures.
