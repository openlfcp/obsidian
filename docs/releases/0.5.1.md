# Shared Tasks 0.5.1

Shared Tasks 0.5.1 makes sharing a section with someone harder to get wrong:
the palette invites to the section you are in, a link of the wrong kind is
refused before it is used, every dead end says what to do next, and a
section marker damaged by a stray keystroke is repaired in one click. For
catalog users updating from 0.5.0.

**Requires Obsidian 1.13.4 or later**, as 0.5.0.

The Markdown format of your notes and the sync protocol are unchanged.

## What changed since 0.5.0

- **"Invite to this section…"** (new command, ID `invite-to-section`)
  invites to the shared section at the cursor, as the pane does. With the
  cursor outside every shared section it says so and opens no picker.
- **The older one-task-at-a-time collaborations step aside.** Their
  commands are named "Legacy: …" and appear only in a vault that already
  holds such a collaboration; "Legacy: Join task collaboration" is always
  there. "Legacy: Invite to task collaboration" (the old
  `invite-collaborator` ID, so hotkeys keep working) lists only those
  collaborations, never shared sections. Pickers that still list both kinds
  say which is which.
- **A link of the wrong kind is refused before it is used.** Joining from
  the pane, or with a palette join, accepts shared sections only. A link to
  an older task collaboration is refused before anything is claimed, says
  what it is and asks you to request a section link; the link still works
  with "Legacy: Join task collaboration". With shared sections off on the
  device, joining from the pane works as before.
- **Dead ends say why and what next.** "Already joined" for an older task
  collaboration, an empty list of shared sections on a device that holds
  only an older collaboration, and "Insert shared section…" with nothing to
  insert yet now name the cause and the next step.
- **A damaged section marker is repaired in one click.** When the start or
  end line of a shared section was changed by a typo (up to two characters)
  and exactly one section on this device matches, the pane shows one
  problem, says that edits to the section are not sent until it is fixed,
  and offers **Restore**, which rewrites only that line if the note has not
  changed since. Otherwise Repair is offered as before. The section shows
  "Damaged in this note" instead of "Not inserted yet", and the pane's main
  action is the fix, never "Insert into a note…".
- **Section markers are protected in Live Preview.** With sharing metadata
  hidden, typing into a marker line is refused, with a short notice that
  points to Source mode; indenting and deleting whole lines still work. A
  damaged marker is hidden too, with a warning mark so you can find it.

## Fixed

- A section whose start marker was changed by one character showed all its
  markers in Live Preview, ignored "Show sharing metadata", and silently
  stopped sending edits ([#89](https://github.com/openlfcp/obsidian/issues/89)).

## Install and upgrade

From Settings → Community plugins → Updates. Nothing to migrate: identity,
keys, shared sections and queued edits are kept.

If you bound a hotkey to one of the older collaboration commands, it does
nothing in a vault that holds no such collaboration, because the command is
not there.

By hand: put `main.js`, `manifest.json` and `styles.css` from the release
page into `<vault>/.obsidian/plugins/shared-tasks/` and compare them with
these checksums.

## Rolling back to 0.5.0

Install 0.5.0 over 0.5.1 (BRAT: choose version 0.5.0 for
`openlfcp/obsidian`, or put 0.5.0's three files into the plugin folder).
The data format is the same; the old command names come back.

## Known limits

As in [0.5.0](0.5.0.md#known-limits), plus:

- Restore covers the start and end lines of a section. A damaged marker
  under a single task (`lfcp-ref`) still goes through Repair.
- Deleting a marker line with Backspace in Live Preview is not confirmed
  separately; Undo brings it back.
- With several cursors, a keystroke that would change a marker line is
  refused for all of them.
- The older collaboration commands appear when the plugin starts or after a
  join; a collaboration that arrives another way shows them after a restart.
